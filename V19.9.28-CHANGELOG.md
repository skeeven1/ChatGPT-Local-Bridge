# V19.9.28 candidate

## Observed failure that triggered this iteration
A real Windows V19.9.27 launch reached local `/readyz` HTTP 200 and Cloudflare reported a registered QUIC tunnel, but the launch process remained blocked in `Public preflight attempt N not ready: fetch failed` for more than 20 attempts.

## Changes
- Public tunnel URL and OpenAPI URL are surfaced immediately after cloudflared allocates the quick-tunnel URL; startup no longer hides the endpoint behind a long blocking preflight.
- Public preflight is bounded and can enter `DEGRADED/PENDING` instead of terminating a locally healthy bridge.
- Background public preflight continues while the bridge stays alive and upgrades endpoint state to PASS if connectivity becomes available.
- Public HTTP probes use Node fetch first and `curl.exe` as a Windows fallback.
- Network errors include nested error codes/messages instead of only `fetch failed`.
- CURRENT-CONNECTION.txt and bridge-endpoint.json are written immediately and updated with PASS/PENDING state.
- Startup banner uses the real bridge version instead of hard-coded V19.8.
- package.json, bridge/runtime/lock versions and active tests are aligned to 19.9.28.
- stable-agent-core manifest default now follows BRIDGE_VERSION rather than hard-coded 19.8.2.

## Scope
This fixes the startup/public-preflight reliability regression. It does NOT claim the Paint rendering bug is fixed; live Paint validation remains pending.
